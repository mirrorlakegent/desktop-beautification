## Phase 1-2 动态壁纸修复（用户「选了视频没效果」）
- 根因：`WallpaperEngine.StartDynamic` 用 `Process.GetCurrentProcess().MainModule.FileName` 取渲染子进程路径，在 `dotnet run` 下指向 `dotnet.exe`，导致子进程变成 `dotnet.exe --wallpaper-host ...`，dotnet 不认该参数直接退出，主界面看不到错误。
- 修复：渲染子进程一律改用输出目录里的应用本体 `DesktopSuite.exe`（apphost），无论主程序以何种方式启动。
- 额外：给渲染子进程加 `RedirectStandardError` + `BeginErrorReadLine`，渲染失败信息写入 `Console.Error`（父进程 `Debug.WriteLine` 捕获），便于排查。
- 用户测试动态壁纸需把 `mpv.exe`（及 `d3dcompiler_43.dll`、`mpv\` 文件夹）放到输出目录 `bin\Debug\net8.0-windows\`。

## Phase 1-2 动态壁纸第二轮修复（3 个真 bug）
1. **mpv 参数用了不存在的选项**（最致命）：`--log-level=error` 在 mpv 中不存在，正确写法是 `--msg-level=all=warn`。mpv 遇到未知选项会**启动即退出**（exit code 1）且无任何窗口——这正是「选了视频没效果」的元凶。
2. **`Process.Start` 被写了两次**：上一轮 Edit 插入 stderr 钩子时留下重复调用，会派生两个渲染进程，第一个不被跟踪、不进 Job Object，永远残留并与第二个争抢同一渲染面。
3. **子窗口坐标用了虚拟屏原点**：`WS_CHILD` 窗口坐标相对父窗口客户区，应从 `0,0` 起；用 `SM_XVIRTUALSCREEN`（左侧副屏时为负数）会把壁纸推出屏幕。

## 第三轮编译修复（CS0165 + 2 个 CS8604）
- **CS0165 `hwndLong` 未赋值**：`App.xaml.cs` 中 `if (hostIdx + 1 >= args.Length || !long.TryParse(..., out long hwndLong))` —— `||` 短路时 `TryParse` 不执行，内联 `out` 变量无法通过确定性赋值分析（编译器不认为 `Environment.Exit` 是不返回的）。修法：把 `long hwndLong = 0;` 提到 if 外部声明，并补 `hostIdx < 0` 的防御分支。
- **CS8604 ×2 `Activator.CreateInstance(Type.GetTypeFromCLSID(...))`**：`GetTypeFromCLSID` 返回 `Type?`，直接传给 `CreateInstance(Type)` 触发可空警告。修法：抽出 `CreateDesktopWallpaper()` 工厂方法，显式判空后抛 `PlatformNotSupportedException`；CLSID 提为 `static readonly Guid` 常量；`GetMonitorDevicePaths` 增加 try/finally 确保 `ReleaseComObject` 与 `PlatformNotSupportedException` 兜底降级到 SPI 路径。

### C# 编译陷阱备忘
- `Environment.Exit()` / `Application.Shutdown()` 在 C# 确定性赋值分析里**不算不返回**，只有 `throw` 和标注 `[DoesNotReturn]` 的方法才算。跟在它们后面的代码仍需保证变量已赋值。
- 内联 `out var` 出现在 `||` / `&&` 短路表达式里时，务必改成外部声明并给初值。

## 第五轮：WorkerW 查找算法再修正（用户诊断仍报 `progman-fallback`）
> 用户运行新版诊断：18 个 WorkerW、DefView 在 Progman 内，但 `predicted strategy : progman-fallback`。说明上一轮"DefView holder 后面 Z 序取 WorkerW + 尺寸≥80% 虚拟屏"的假设在该机不成立。

### 根因分析
- 形态 B（DefView 在 Progman）下，真实壁纸 WorkerW 可能不在 Progman 之后，或尺寸未达虚拟屏 80%，或 Explorer 尚未初始化、需要 `WM_SPAWN_WORKER` 才创建。
- 旧算法在 PreviewStrategy（无副作用）里只能看现有窗口，所以报 fallback；`Acquire` 若也找不到就会真的退化到 Progman。

### 修法
- `WorkerWHost.cs` 再次重写：
  1. `FindExistingUsable`：先尝试 Z 序后邻规则，失败后改用**最大非-DefView WorkerW**（尺寸≥虚拟屏 25% 即可）。
  2. `Acquire` 核心改**快照-生成-找 newcomer**：先拍现有 WorkerW 集合，发送 `WM_SPAWN_WORKER`，再枚举找出集合里没有的新 WorkerW，取其中最大且可见者。这不再依赖 Z 序邻接假设。
  3. 若生成两次仍失败，最后做一次 `WaitForExistingTarget` 兜底。
  4. `PreviewStrategy`：无现有可用 WorkerW 时返回 `workerw-will-spawn`（更准确，避免误报 `progman-fallback` 吓人）。
- `WallpaperDiagnostics.cs`：WorkerW 列表加上 `vis` 与 `WxH` 尺寸，便于看清每个 WorkerW 的底细。
